# Mac 微信界面采集试跑记录

更新：2026-09-23。这里仅记录采集能力和缺口，不包含文章正文或用户凭据。

## 已验证的链路

1. 人在 Mac 微信打开目标公众号主页，程序用窗口标题和主页 OCR 核对账号。
2. 程序识别历史文章卡片，模拟点击，复制微信内置文章窗口中的真实链接与可选择正文。
3. 打开文章底部核对公众号名称；不一致时拒绝入库。
4. 按真实链接去重，分别保存正文与公开可见数字，写入 SQLite 和断点文件。
5. 中断后从同一工作区续采；`audit` 输出每层覆盖率和缺失原因。

示例目标为“监所家属”。本地工作区在试跑停止时共有 158 条不同链接，其中 155 条由当前 Mac 微信界面采集并关联目标账号，151 条界面采集记录带有效正文；这 155 条都记录了阅读数和点赞数。工作区另有 3 条较早的样例/历史采集记录，审计总数会包含它们。微信主页当时显示“301篇原创内容”，程序没有证据证明历史列表已到末尾，检查点仍为未完成。转发、旧点赞、评论数和评论明细没有达到全量门槛。

这足以验证界面操作、账号校验、去重、正文与两项数字入库的技术链路；它不证明整个账号已经读完。

## 可复用试跑

先在微信中打开目标文章，点击公众号名称进入主页，并确认主页名称与文章作者一致。安装依赖后运行：

```bash
uv sync --extra mac --extra dev
.venv/bin/gzh-reader doctor
.venv/bin/gzh-reader collect \
  --url '<目标公众号的一篇文章链接>' \
  --account-name '<微信主页显示的名称>' \
  --max-articles 20 \
  --output '<数据根目录>'
```

`--max-articles` 是该工作区累计保存的文章数量上限。试跑后读取 `<数据根目录>/<公众号名>/audit/coverage.json`，核对目标账号、正文和字段覆盖率。继续试跑可执行：

```bash
.venv/bin/gzh-reader resume --workspace '<数据根目录>/<公众号名>' --max-articles 40
.venv/bin/gzh-reader audit --workspace '<数据根目录>/<公众号名>'
.venv/bin/gzh-reader export --workspace '<数据根目录>/<公众号名>'
```

去掉 `--max-articles` 才是持续续采。运行期间需保持微信可见；工作区数据不会进入 Git 仓库。源码采用 MIT License 的独立实现，没有复制参考 Windows 项目的代码。

## 批量阶段还需解决

- 给 Vision OCR 和窗口操作设置进程级超时；本次长批次在第 4 次卡片尝试后停滞，已停止并保留断点。
- 证明历史列表确实到达末尾；连续相同视口只能记录为未完成。
- 对正文和五项互动字段分别审计。当前桌面页面没有稳定提供所有转发、旧点赞、评论数或评论明细，缺失必须保持未知。
- 首次只粘贴一篇文章链接就自动抵达账号主页尚未实现；现阶段需要先在微信中打开主页。

批量读取的主要循环应由确定性程序执行，不需要逐篇调用大模型。若后续接入低成本模型（例如 DeepSeek API），只把 OCR 无法判定的少量片段送去复核；接入前需要明确接口、费用和待发送的数据范围。当前仓库尚未配置或调用任何模型 API。

# Mac 微信界面采集试跑记录

更新：2026-09-26。这里仅记录采集能力和缺口，不包含文章正文或用户凭据。

## 历史上局部验证的链路（当前版本仍需端到端复验）

1. 人在 Mac 微信打开目标公众号主页，程序用窗口标题和主页 OCR 核对账号。
2. 程序识别历史文章卡片，模拟点击，复制微信内置文章窗口中的真实链接与可选择正文。
3. 打开文章底部核对公众号名称；不一致时拒绝入库。
4. 按真实链接去重，分别保存正文与公开可见数字，写入 SQLite 和断点文件。
5. 中断后从同一工作区续采；`audit` 输出每层覆盖率和缺失原因。

示例目标为“监所家属”。截至 2026-09-23 的本地核查：工作区有 162 条不同文章记录，但最新正文文件仅 43 篇通过有效正文检查；数据库原先标为 `ok` 的另 112 篇属于误标，其中 110 篇只有 URL。阅读数非空 162 篇。微信主页显示“301 篇原创内容”，但历史列表没有到达末尾的完成证据；转发、旧点赞、评论数和评论明细仍未形成可靠的完整采集链路。上述数目仅为本地试跑快照，不应当作全量结果。

历史记录证明部分文章曾经通过界面操作入库，但大量“只有链接的正文”被误标为成功；因此当前版本仍需重新完成端到端小样本验收，更不证明整个账号已经读完。

## 可复用试跑

先在微信中打开目标文章，点击公众号名称进入主页，并确认主页名称与文章作者一致。安装依赖后运行：

```bash
uv sync --extra mac --extra dev
.venv/bin/gzh-reader doctor
.venv/bin/gzh-reader collect \
  --url '<目标公众号的一篇文章链接>' \
  --account-name '<微信主页显示的名称>' \
  --max-new-articles 5 \
  --output '<数据根目录>'
```

`--max-articles` 是该工作区累计保存的文章数量上限，可省略；`--max-new-articles` 是每轮新增上限，默认 5 篇。试跑后读取 `<数据根目录>/<公众号名>/audit/coverage.json`，核对目标账号、正文和字段覆盖率。继续试跑可执行：

```bash
.venv/bin/gzh-reader resume --workspace '<数据根目录>/<公众号名>' --max-new-articles 5
.venv/bin/gzh-reader audit --workspace '<数据根目录>/<公众号名>'
.venv/bin/gzh-reader export --workspace '<数据根目录>/<公众号名>'
```

每轮最多新增 5 篇，需由用户决定是否再启动下一轮；不会自动连续跑到账号全量。运行期间需保持微信可见；工作区数据不会进入 Git 仓库。源码采用 MIT License 的独立实现，没有复制参考 Windows 项目的代码。已验证阶段的优先目标是形成可复用、可审计的样本采集流程，然后再用确定性程序执行批量循环；DeepSeek 只可选地复核公开列表 OCR 文字，不负责逐篇点击。

## 微信 4.1.x 标签页适配与失败恢复

- 新版微信将公众号主页和文章放在同一个 `微信 (窗口)` 的不同标签中。程序必须在每次点击前核对当前页面是目标账号列表，在文章打开后核对卡片标题和底部作者；标题或作者不一致不得入库。
- 主页向下滚动后，“301 篇原创内容”会折叠；此时须用顶部账号名、列表导航和阅读数共同确认主页。Vision 可能把“全部 文章”并为一行、把账号图标误识别为前缀，因此不要求 OCR 行完全相等。
- 正文里可能有“亲情邮”等小程序卡片。复制时只聚焦已核对的文章标题，不点击文章中央的小程序卡片；若出现“即将打开小程序”，只能选“取消”，不能选“允许”。正文不足以验证时保留 `missing`，不得计入新增成功。
- 新版微信可能让新文章沿用上一页的靠下阅读位置。程序只在目标文章标签被确认后，把右侧滚动条拖回顶部，再用正文标题核对；不能因顶部暂时看不到标题就判为“未打开”。
- OCR 误读卡片标题或列表在滚动后重排时，点击可能打开另一篇文章。标题校验失败后必须关闭当前文章、重新确认目标账号列表并重新 OCR；不能直接使用上一视口的下一张卡片坐标。无法恢复主页时立即停止。
- 旧版数据使用 `human-...` 内部账号 ID，新版使用 `human:...`。断点查询按账号名称与 `mac_human_agent` 来源合并两者，避免把已完成文章重复打开；真实文章 URL 仍是稳定去重键。

以上保护已有本地单元测试；小程序弹窗和错误卡片的失败路径也在实机观察过，但长批次稳定性尚未验收。现在任一文章采集步骤失败、白屏、退出登录或账号身份不符，均应停止该批次，不自动打开下一篇。

## 批量阶段还需解决

- Vision OCR 已移入独立子进程并设置 12 秒硬超时；超时后保留断点并输出审计。本次长批次曾在第 4 次卡片尝试后停滞，故仍需继续验证其他窗口操作是否可能卡住。
- 证明历史列表确实到达末尾；连续相同视口只能记录为未完成。
- 对正文和五项互动字段分别审计。当前桌面页面没有稳定提供所有转发、旧点赞、评论数或评论明细，缺失必须保持未知。
- 首次只粘贴一篇文章链接就自动抵达账号主页尚未实现；现阶段需要先在微信中打开主页。

批量读取的主要循环由确定性程序执行。DeepSeek 与豆包已可选地复核 OCR：仅在本地规则找不到卡片时发送公众号列表的公开文字，最多 5 次/运行；现有实现不发送文章正文或截图。模型只返回候选行号，程序仍从原始 OCR 行验证文字、数字和坐标。未提供密钥或未勾选时不调用 API；两家的模拟响应测试已通过，真实连接仍待验收。

## 2026-09-26 进度与阻碍

- 新增“误点小程序后取消并停止”的保护，覆盖等待文章、复制链接、复制正文三个入口；此前取消弹窗后可能继续操作旧页面。回归测试通过，尚未实机复验。
- 启动检查改为查询系统实际安装的微信应用，不再把 macOS 自带 `open` 命令误判为微信已安装。
- 电脑控制通道能读取当前微信窗口截图，却连续两次拒绝鼠标点击并返回 `noWindowsAvailable`；键盘搜索随后可用。尝试在搜索框粘贴目标名称时，微信弹出“为了你的账号安全，请重新登录”。我们没有点击确认、没有继续登录或启动文章采集器；不能仅凭时间邻近证明粘贴动作就是退出原因。本轮没有新增文章记录。
- 本机 `ARK_API_KEY` 环境变量存在，但包含 API 请求头无法编码的字符；真实豆包测试在发出请求前失败。程序现在给出脱敏的中文错误。应在图形界面中临时输入有效的火山方舟密钥后再验收，不要把密钥发到聊天或写入仓库。
- 程序现能识别明确的重新登录弹窗，停止窗口操作并把任务原因记为 `wechat_login_required`；不会自动关闭该弹窗或重新登录。当前完整测试为 80 通过。待微信恢复登录后，下一步仍是实机单篇：先打开目标主页，再验证误点时安全停止、正确文章的链接/正文/页尾和返回主页；通过后才能进入 10 篇、50 篇批量验收。

### 重新登录后的单篇复测（2026-09-26）

- 用户确认已重新登录后，以 `--max-new-articles 1` 运行一次。采集器在 `open_profile` 阶段停止，没有点击文章，也没有新增归档；当时的错误是“微信主窗口中没有看到用于恢复的示例文章链接”。
- 同一窗口随后通过本机 Vision 读取到 0 行文字；电脑控制工具读取微信及访达的截图也都是白色。因此**不能推断用户看到的微信真的白屏**，只能确认当前自动化画面不可读。`doctor` 的屏幕录制权限检查为真，但授权检查不等于实际截图可读。
- 已增加空/不可读窗口的显式停止提示和回归测试，禁止在无法识别界面时继续点击。下一次实机验证前，先确认电脑控制工具或本机 Vision 可以实际读到微信聊天列表/目标主页，再启动单篇采集；不要因 `doctor` 全绿而跳过这个门槛。
- 本次既未验证单篇端到端，也未验证批量读取；仍不得宣称“全量”或发布可复用流程为已验收版本。

后续 W01 诊断进一步确认：`doctor --visual` 的本地测试窗口截图及 OCR 成功，微信主窗口可见但 OCR 0 行；系统窗口元数据中的 sharing state 为 `0`，整屏截图在该窗口区域也未识别到文字。用户确认其肉眼看到正常聊天列表，因此不能归因于微信真实白屏。已分别验证旧 Core Graphics 窗口截图与 ScreenCaptureKit 单帧截图，后者同样得到 0 行；没有把未证实的替代截图技术接入采集器。图形向导现提供“检查能否读取微信画面”，采集器保持停止条件。下一步需实测微信文章/公众号子窗口是否可共享，或找到受支持的界面信息入口。

后续离线工作已加入受限 Agent 决策层：DeepSeek 或豆包可以对当前视口中的已识别文章排序或暂停，程序拒绝重复、虚构编号；尚不是完整的跨页面工具调度。网页采集已改为独立子进程，连续 120 秒没有动作进展会终止本仓库的采集进程，界面也提供“停止本轮”。真实子进程和无效密钥的错误回报已在测试中验证；新的网页进程管理仍需实机采集验证。当前完整测试为 90 通过。

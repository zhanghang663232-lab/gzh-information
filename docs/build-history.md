# gzh-information 构建复盘：为什么现在这样做

更新：2026-09-27。本文按决策和实机证据回顾项目，不把旧计划当作当前已实现功能。给低成本模型接手时，先读本文，再读 [故障手册](troubleshooting.md)、[Agent 起步说明](agent-start.md) 和最新 [验收记录](acceptance/run-2026-09-27.md)。

## 一直不变的目标

用户给出目标公众号的一篇公开文章链接；在 Mac 上可恢复地批量读取**同一账号**普通用户可见的文章正文、阅读、点赞、旧点赞、分享、评论计数及可见评论/回复；明确列出不可得字段；把可复用的程序放进 GitHub。优先级调整过：先取得足够多的可信样本，证明流程可复用，再扩大批量并让低成本模型参与。10 篇是小样本验收，不是“整个账号读完”。

一篇可信记录的必要链条：目标账号主页 → 当前卡片 → 打开的正确文章 → 从微信复制的真实 URL → 正文/公开数字的可见证据 → 文件和 SQLite 保存 → 下次能识别同一 URL。账号、标题或正文缺证据时，不能凭模型猜测补上。

## 构建过程与每次转向

| 阶段 | 当时做了什么 | 得到的证据与结论 | 对现在的约束 |
| --- | --- | --- | --- |
| 1. 研究 Windows 参考项目 | 研究 [`Access_wechat_article`](https://github.com/yeximm/Access_wechat_article) 的微信 UI 触发、批量队列和异常恢复。 | 其具体实现依赖 Windows UI 库和窗口技术，不能在 Mac 直接运行；许可证也不能当 MIT 源码复制。 | Mac 控制层独立实现，只借鉴任务队列、身份核对、断点与审计思想。 |
| 2. 调研下载器/导出服务 | 试过桌面文库、链接批量下载与导出服务思路。仓库旧版 `wechat-archive` 使用第三方列表 API。 | 单篇正文下载不等于完整历史列表，也不能保证阅读/分享/评论；导出服务曾出现认证/可用性问题。 | 当前 Mac v2 默认走**桌面微信可见界面**，不要要求 `down.mptext.top` key。旧脚本保留为历史实验。 |
| 3. 明确界面路线 | 用户指定像 Windows 项目那样通过 Agent 操作电脑，不采用出口不稳定的网站作主路径。 | 首次仍需要用户在微信中打开目标账号主页；只粘贴链接自动进入账号尚未完成。 | 图形向导负责启动与反馈；本地 Mac 程序负责截图、点击、复制和保存。模型 API 只处理有限文字判断。 |
| 4. 建立 v2 数据层 | 建立 `src/gzh_reader`、SQLite、断点、导出、覆盖率与缺失账本。 | 旧工作区曾有大量“只有 URL 却标正文 ok”的记录；记录数不能代表有效正文数。 | 分层核验正文、指标、评论；最新快照与有效正文文件才可计入验收。历史数据库不删除、不冒充本轮新增。 |
| 5. 适配 Mac 微信新版 | 微信 4.1.x 出现合并/分离窗口、文章标签、滚动位置继承；台前调度使窗口变缩略图。 | 聊天主窗口肉眼可见时，自动化仍可能 OCR 0 行、共享状态为 0；公众号/文章子窗口曾可读。关闭台前调度后，宿主机纯后台输入仍未通过。 | 当前宿主机流程要求**可见微信窗口**，先核对实际截图可读，再点击。后台 VM 是未验收方向。 |
| 6. 处理误点与卡死 | 发现旧坐标点进小程序、同名文章标签、菜单误识、父进程截图干扰后续 OCR、Vision/PyObjC 退出崩溃、失败后二次关闭窗口。 | 每一项都有本机观察或故障记录；对应保护已逐步进入代码。 | 每篇后重新 OCR；目标菜单/标签和账号身份必须核对；小程序弹窗只取消并暂停；截图/OCR 放在有超时的一次性子进程。 |
| 7. 处理重复与数字错误 | 续采会重复打开旧文；阅读数变化导致旧签名失效，视口位置提示曾被误当真实 URL；OCR 把相邻数字粘连、把普通阅读数误读为“万”。 | 出现过“打开 3 次、新增 0 篇”和异常数字。后来改为以真实 URL 为最终身份，卡片/视口只辅助导航，指标交叉核对。 | `attempts` 与 `new_in_run` 必须分开报告；复制新链接后核对标题与账号，字段缺失保持未知。 |
| 8. 排查微信退出登录 | 用户观察到约 30 篇后退出，也观察到更新微信后单次读取即退出；另有独立微信客户端崩溃报告。 | 没有证据证明固定阈值或某一个具体动作是根因。后来 1、3、5、10 篇受限批次未见退出。 | 单批有上限并保存断点；明确登录提示立即停止。不能把 10 篇成功写成长期无风险，也不能靠换号/IP规避。 |
| 9. 接入低成本模型 | DeepSeek、火山方舟豆包共用公开列表 OCR 复核与有限候选排序协议。 | 本地模拟测试已通过；目标账号最近 10 篇实机批次未启用模型，豆包真实 API key 曾无效。 | 模型没有天然 Computer Use 权限；本机程序执行动作、校验结果。不能把“适配器代码存在”写成“双模型实机已验收”。 |
| 10. 小批量实机验收 | 在“监所家属”目标账号逐级试跑单轮 1、3、5、10 篇。 | 最后单轮 10 次打开新增 10 个不同 URL，10 份正文通过最低文件检查；工作区累计 66 份可核查正文。本轮阅读/点赞/评论计数各 10/10，分享 0/10。 | 这是正文小样本可行性证据；列表末尾、旧点赞、分享、评论明细和干净 Mac 重复仍未通过。 |
| 11. 交付与外部试跑 | 建立双击脚本、源码体验包、GitHub CI 和草稿 PR；豆包从 GitHub 默认 `main` 误进旧脚本。 | 豆包报告的导出 API key 与旧 UA 问题属于 `wechat-archive`，不能诊断 v2。`main` 首页和旧版目录已加入口警示；v2 有独立起步说明。 | 接手先查分支。当前 v2 在 `codex/v2-macos-validated`，草稿 PR #2 尚未作为全量版本合并。 |

## 两个最重要的纠错

1. **“可以读一篇”不是“可以读整个账号”。** 历史列表要有到末尾的可核验证据；每篇正文要有真实 URL、账号核对和有效文件；互动字段分别计算覆盖率。主页显示的原创篇数只可作为待核对的参考，不是采集完成信号。
2. **“模型会操作电脑”需要本机执行器。** DeepSeek/豆包可判断 OCR 行、候选顺序或暂停；只有已安装、获得权限并看到微信窗口的 Mac 程序能执行点击、滚动、复制与保存。模型返回“成功”不能替代数据库和文件证据。

## 2026-09-27 的交付状态

- 可用：中文本地向导、Mac 可见界面的小批量正文路径、SQLite 续传、逐字段缺失账本、审计和导出、DeepSeek/豆包适配器代码、可双击的 Apple Silicon 源码体验包。
- 已实机验证：目标账号单轮 10 篇新增正文的最低检查；阅读/点赞/评论计数按上述样本有值。最近一轮没有观察到退出登录。
- 尚未验证：只给链接即可自动进入账号、完整历史列表末尾、五项互动覆盖率、公开评论与回复全量、超过历史故障点的长批次、第二台干净 Mac、两个供应商的真实 Agent 采集。
- 仓库状态：v2 在 `codex/v2-macos-validated`，PR #2 为草稿。用户后来要求暂停把仓库改公有；截至本记录，仓库仍为私有。公开化不是本文流程的一部分。

下一次运行由 [故障手册](troubleshooting.md) 的固定顺序启动。遇到与本文不同的新现象，先留下脱敏的 `stop_reason`、失败阶段和运行时间，再改动代码；不要把未证实的原因写成结论，也不要无上限重跑。
